# Standalone WiZ commissioning: evidence and next experiment

Checked 2026-11-16. This is a research result, **not a completed pairing implementation**. No bulb, account, Mac network setting, production firmware, or private home export was changed or read by this task. The exported key remains private. A final product that owns discovery, commissioning, key management, control and recovery without the WiZ app is still the target.

The hardware team subsequently reached **one existing-home bulb** through the spare USB hub and OnePlus hotspot. Read-only replies identified **`ESP25_SHRGB_01`, firmware `1.38.0`**, reported 2200–6500 K capability and a current UTC response to `getTime`. No signed write, reset or pairing was performed in that check. These are hardware-team observations, not results reproduced by this static-analysis task; they identify this one bulb, not all exported devices.

## What is established

Local control after provisioning and complete independent commissioning are separate capabilities. WiZ's published TypeScript library implements UDP control, state queries and application registration; it does not provide a new-home/key provisioning lifecycle. Its `registration` operation is an application notification subscription, not ownership enrollment. [Vendor source, pinned revision](https://gitlab.com/wizlighting/wiz-local-control/-/tree/b7bfe09fa480c214d67dcb6b151afef3e0c23416)

The consumer installation guide documents Wi-Fi broadcast, Bluetooth and the bulb's temporary `WiZConfig_xxxx` AP as transports for credentials. It does not publish their wire contracts. “No sign-in required” means an external identity provider is optional; it does not establish cloud-free home creation. WiZ describes its cloud as the source of truth for security and synchronization. [Official installation](https://wizconnected.helpshift.com/hc/en/7-wiz-v2/faq/527-adding-wiz-lights-in-your-home/), [official network requirements, pp. 4–7](https://assets.wizconnected.com/manuals/WiZ-Network-Configuration-v2-01162024.pdf)

The `50ck/wiz` source gives a concrete manual transport: identify with `GET /device`, submit `POST /pairing`, reconnect on the target LAN, then `POST /complete`. Its payload includes encoded Wi-Fi credentials, `hid`, region/environment and time. However, it fixes `hid` to `420`, contains no home-key installation, and its author reports unpairing after WiZ MQTT contact. This establishes a limited offline experiment, **not** a safe default for existing homes or authenticated local control. Merely substituting the real home ID does not prove enrollment authorization or key delivery. [Pinned pairing implementation](https://github.com/50ck/wiz/blob/80624dce3cd381e08f986d13df83b1dce2828fc1/src/wiz/pairing.py), [HTTP sequence](https://github.com/50ck/wiz/blob/80624dce3cd381e08f986d13df83b1dce2828fc1/src/wiz/protocol.py), [author's limitation](https://github.com/50ck/wiz/blob/80624dce3cd381e08f986d13df83b1dce2828fc1/README.md)

## Earlier reference: ESP24, not the measured bulb

The `alxgmpr/wiz-re` author tested **ESP24_SHRGB_01 1.30.1** and analyzed **1.36.1**. Its method catalog identifies `setSecurity`, `setWifi`, `setPairingAssist` and `regLight` as MQTT-gated. It provides no complete consumer account-independent bootstrap or `setSecurity` parameter description. Its interception/firmware-patching experiments are not evidence that current bulbs accept a replacement server or modified firmware safely. [Pinned protocol research](https://github.com/alxgmpr/wiz-re/blob/a03f3b004afec92280bdcd019d348086d4f35eeb/PROTOCOL.md), [scope and tooling](https://github.com/alxgmpr/wiz-re/blob/a03f3b004afec92280bdcd019d348086d4f35eeb/README.md)

An independent static check downloaded **one public reference image**, using the exact module/version URL in that project's downloader. It was never executed or flashed. The transfer used the vendor's HTTP endpoint; HTTPS refused connection. Its hash identifies the inspected bytes and is not a vendor signature/authenticity proof.

## Matching ESP25 1.38.0 static evidence

The documented public image URL convention returned `ESP25_SHRGB_01/1.38.0/wizlight.bin`: **1,777,664 bytes**, SHA-256 **`e47c465c420568682a7a7e77ed051c1898ddc272a98b7af73634c43f22310167`**. Its ESP image chip ID is 5 and it contains `1.38.0` version strings. The URL matches the observed module/version, but the physical bulb's installed image hash was not read, and HTTP download plus a locally calculated hash is not vendor authenticity verification. [Matching public image](http://firmware.wiz.world/firmwares/ESP25_SHRGB_01/1.38.0/wizlight.bin)

Independent disassembly used explicit RV32IMC ELF attributes: raw-binary disassembly can misread compressed `c.jal` instructions as RV64 `addiw`. Findings:

| Path | Exact matching-image observation | Boundary |
| --- | --- | --- |
| `setSecurity` | Table `0x3c191efc`, handler `0x420d7aa2`, flag `0x4`. Reads `confTs`, `udp`, `key`; candidate array order is ciphertext string, IV string, two integer offsets. Decoder requires a 16-byte result; settings use the 18-byte `sec` record. | This is not yet an authorized local request contract. |
| `setWifi` | Handler `0x420d73dc`, flag `0x4`. Reads `period`, `retries`, `iv`, `offsets`, `enc_ssid`, `enc_pwd`; shares the security handler's decoding functions. | Signed `setPilot` support does not prove signed UDP Wi-Fi migration is permitted. |
| HTTP pairing | `/pairing` handler `0x420acea2` reads encrypted Wi-Fi fields plus `token`, `off_comm`, `hid`, `env`, `reg`. | Do not invent a request using these names. |
| Offline branch | `off_comm` selects event `0x40000000`; `0x420cf26e` calls completion `0x420d0d1c`, which persists supplied home metadata and a separate 17-byte `offlineComm` token/flag record through `0x42012584`. | It establishes an offline setup branch, **not** UDP signing-key installation, existing-key preservation, or later cloud acceptance. `offlineComm` is distinct from `sec`. |
| Queries/time | `getTime` is in the dispatch table; neither a `getSecurity` nor `setTime` method string occurs in this image. `ntp.wiz.world` does occur. | No supported local security readback/time setter was established. |

The decoding helper uses the same embedded public certificate as `50ck/wiz`, apart from a trailing newline; offsets select a certificate slice. That confirms a shared encoding lead, not source authorization or robust setup. Full factory enrollment remains open on the measured model. Separately, a first-hand researcher reports signed UDP working on this same module/version using the official exported home key; that corroborates the control path, not standalone commissioning. [Same-model signing research](https://gist.github.com/rmcolber/ccb5d804c36270efd1e1dfd239efe740)

The follow-up static trace narrows the offline branch further: its16-byte token is later serialized as `regLight.params.token` over the registration path; a successful result clears the17-byte pending record. HMAC independently reads the first16 bytes of `sec`. Thus `offlineComm` is deferred registration, not a demonstrated owner-key installer. Normal UDP ingress uses source index1, which fails `setSecurity`'s transport mask `0x04` before HMAC verification; possessing the current home key does not grant that method over normal UDP. A separate scan/test-mode dispatch exception exists, but no normal pairing route into it or safe lifecycle has been established. It is an unqualified research lead, not an onboarding feature. These are static findings from the [matching public ESP25 1.38.0 reference image](http://firmware.wiz.world/firmwares/ESP25_SHRGB_01/1.38.0/wizlight.bin), not the installed image's verified hash or hardware acceptance. Reproducible excerpts are retained locally in `offline-comm-trace.md` and `offline-comm-evidence.txt` beside the disassembly.

## Smallest useful next experiment

The next test should be **one existing bulb, preserving its real home and key**, before any reset:

1. Establish a development network path without changing the Mac's Wi-Fi. The current ESP AP has no NAT, so its campus uplink does not provide bulb Internet access. Either qualify bounded, owner-enabled AP forwarding/DNS on the installed ESP, or use a temporary separate commissioning network. Do not claim official setup succeeds until the bulb itself reaches the required services. A temporary network must not compete with the final AP using the same credentials simultaneously.
2. The hardware team's initial identification/time check is now complete for one ESP25 1.38.0 bulb. Preserve those replies, match its full MAC to the selected exported bulb, and obtain any still-missing capability/user-state reads. A DHCP lease or WiZ-looking SSID is insufficient identity evidence.
3. Establish a signed-command baseline with the privately imported real key, then verify unsigned and wrong-key rejection if verified-only mode is selected. The current owner-selected **Allow all controls** setting intentionally does not meet that rejection gate; preserve that choice and report the LAN bypass risk rather than silently switching it. Record command acknowledgment and observed state separately. This proves enforcement only for the tested model/version/settings. WiZ documents verified-only control, but key possession alone does not prove that the device rejects unsigned traffic. [Official local-security setting](https://wizconnected.helpshift.com/hc/en/7-wiz-v2/faq/548-secure-or-disable-local-network-communication/)
4. Block vendor cloud access while retaining the selected local LAN and a controlled time service. Test bulb cold boot, gateway cold boot, simultaneous cold boot and a long offline interval. Observe actual DNS/NTP requests; do not assume `getTime` is a setter or that gateway clock synchronization sets the bulb's clock. If the bulb uses the observed vendor NTP hostname, a local DNS/NTP compatibility service is a concrete candidate, but must return trusted time and be qualified on that bulb.

Steps 1–4 can establish an independent **operating** lifecycle for already provisioned bulbs. They do not close new-bulb onboarding.

### Preserve-home migration to the final AP

For this development phase, the most defensible migration experiment uses the official app's **Bluetooth reinstall while retaining existing settings**, which the vendor's current release history explicitly advertises. Record home/MAC/key-verification baseline first; select the existing bulb and retain its home rather than deleting/re-adding it. The release note does not guarantee that reinstallation succeeds onto an Internet-less target. [Official release history](https://apps.apple.com/us/app/wiz-connected/id1587655962)

If direct reinstallation onto the production AP cannot finish without Internet, stage it on a **temporary Internet-backed AP using the final AP's exact SSID/password**, while the production AP is temporarily disabled. After official migration completes, disable the temporary AP and restore the production AP. WiZ explicitly documents that changing routers with unchanged SSID/password requires no new setup. This handoff preserves credentials rather than claiming the current ESP already provides NAT; it still requires an owner-controlled temporary AP, an explicit recovery plan and hardware verification. It does not require changing the Mac's Wi-Fi. Do not rename or disable either AP automatically as part of research. [Official router-replacement guidance](https://wizconnected.helpshift.com/hc/en/7-wiz-v2/faq/683-how-many-wiz-devices-can-i-connect-in-my-home/)

After handoff, compare home/MAC/capabilities and verify the same signing key before considering migration successful. Retain the known-working hotspot as the recovery path until this passes. This temporary official-app step is development bootstrap; it does not satisfy the final independent-onboarding requirement.

### Smallest candidate for cold-boot time

The production AP presently has neither general NAT nor a hardware-qualified DNS/NTP service. The isolated lighting candidate now implements bounded AP-only **DNS for `ntp.wiz.world` plus SNTP on UDP123** inside its existing worker. The pinned DHCP server already offers the AP as DNS; the helper refuses conflicting configuration instead of changing DHCP or clearing leases. Only current associated DHCP peers receive replies, with per-MAC/global rate limits and one packet per iteration. No general forwarding is implied. Parser, time, rate and mocked socket/lease lifecycle checks pass; C3 compilation passes. Actual bulb cold-start DNS/NTP convergence is still untested. See the [runtime helper contract](../../lights/firmware/runtime/README.md#ap-local-bulb-clock-helper). Firmware contains `ntp.wiz.world`, but the actual cold-start trace must confirm how it is used.

The responder must use the gateway's established trustworthy UTC, echo the client's originate timestamp correctly, and never serve boot-relative or stale fabricated time. If the gateway itself lacks trustworthy time after simultaneous cold start, signed control must stay unavailable until time is recovered; retained last-known time alone is not current UTC. No private WiZ API or bulb `setTime` request is implied. Verify `getTime` convergence and signed-command/readback after bulb-only and simultaneous power loss. [NTP packet/time semantics, RFC 5905](https://www.rfc-editor.org/rfc/rfc5905.html)

For the missing commissioning lifecycle, use a separately selected, recoverable test bulb/home during development. Capture the official app's legitimate manual/Bluetooth provisioning and subsequent bootstrap at an owner-controlled gateway or phone trace, with credentials and key material retained only in protected local artifacts. Correlate `/pairing` acceptance, DHCP/MAC, first cloud registration, security-setting delivery and final local verification. Encrypted traffic metadata alone cannot reveal the key-installation payload; do not label an encrypted packet capture a recovered protocol. Do not rotate the live home's key, change the bulbs' cloud destination, or replay cloud messages merely to obtain a trace.

Then reproduce only observed messages on that matching model/version, with a locally generated home key, and prove: persistence after power loss, verified-only enforcement, key rotation, removal/re-enrollment, failed setup recovery, loss of time, and no later unpairing. A copied cloud home number or the `420` workaround is not that proof. If the accepted key-install path requires authenticated vendor bootstrap, a stock-firmware native flow has not yet been established; a vendor-supported integration or a different qualified commissioning protocol would be required.

## Alternative and release boundary

Matter may provide a separate local trust fabric on compatible hardware, but compatibility and setup-code availability must be checked per bulb. WiZ documents older compatible devices obtaining their Matter certificate/code through its app, and app-triggered commissioning windows. Firmware version alone does not prove a printed setup code, app-free factory enrollment, full WiZ feature parity, or room for a Matter controller beside this ESP's display workload. It is a candidate for a later measured experiment, not a silent replacement for the present protocol. [Official Matter setup](https://faq.wizconnected.com/hc/en/7-wiz-v2/faq/592-how-to-install-my-matter-ready-device-to-matter-hub/), [official compatibility/setup limits](https://wizconnected.helpshift.com/hc/en/7-wiz-v2/faq/594-matter-setup-tips/)

The final UI must not claim standalone onboarding is finished while it still requires the WiZ app/export. The development export can unblock signed control and the preservation-first experiment now; the firmware evidence supplies a focused next research target for replacing that dependency.

They contain no user export or key. No physical qualification was performed in this research task.
