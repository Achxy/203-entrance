# WiZ light integration: protocol and product research

Research date: 2026-11-16. This is a source audit and implementation recommendation, not a claim that the room's bulbs have been paired or controlled. No bulb commands, resets, commissioning writes, or firmware updates were performed for this audit.

## Conclusions that determine the design

The requested everyday controls can use WiZ's local UDP protocol behind an authenticated ESP32 gateway. The Mac needs to speak only to that gateway, through the Internet relay or our own authenticated Bluetooth service. This Bluetooth path is **Mac → ESP32**, not an invented WiZ bulb Bluetooth protocol. Bulb discovery and control require a reachable local network. [WiZ local-control source](https://gitlab.com/wizlighting/wiz-local-control), [pywizlight discovery](https://github.com/sbidy/pywizlight/blob/19e607afe0eb6db1473602639e194d691234d4fd/pywizlight/discovery.py)

Use a private, password-protected 2.4 GHz bulb network; use campus Wi-Fi only for the gateway's outbound Internet connection. WiZ explicitly supports WPA2/WPA3 Personal and does not support open networks. Campus client isolation is an additional obstacle to direct gateway-to-bulb traffic. A private LAN also prevents guests from bypassing application permissions through legacy unsigned UDP. This topology is a recommendation derived from the documented network requirements and this project's campus constraints. [WiZ network requirements](https://wizconnected.helpshift.com/hc/en/7-wiz-v2/faq/490-what-type-of-networks-does-wiz-support/)

“Full parity” must be split into everyday control, equivalent features implemented by our gateway, and WiZ-specific administration. Existing libraries do not establish universal, app-free consumer commissioning or universal UDP access to native schedules, SpaceSense, accessories, firmware management, or all persistent configuration. Never expose a button that silently sends a guessed method. Label each feature as supported, model dependent, needs official setup, or unavailable.

Newer WiZ firmware supports authenticated local commands with a home security key. WiZ's documented **Only verified controls** setting is preferable to an open local-control network. The key belongs in the trusted gateway and owner setup flow, never in distributed guest software. Rotating it can remove third-party integrations. This is separate from our admin key and guest sessions. [WiZ local communication security](https://wizconnected.helpshift.com/hc/en/7-wiz-v2/faq/548-secure-or-disable-local-network-communication/)

### Why method names alone are insufficient

The vendor repository exposes methods which particular consumer firmware may decline over UDP. A separate author's direct firmware study of `ESP24_SHRGB_01`, tested on 1.30.1 and analyzed against 1.36.1, reports `setUserConfig`, `setFavs`, `setWiZClick`, `setSchd`, `setWifi` and `updateOta` as MQTT-only there. This is useful first-hand implementation evidence, not a universal vendor guarantee or a reason to bypass vendor security. It directly prevents treating the vendor library's surface as a promise of consumer UDP parity. [Firmware study and declared scope](https://github.com/alxgmpr/wiz-re/blob/main/PROTOCOL.md)

## Commissioning and “no WiZ cloud” boundaries

### Existing bulbs already on the private LAN

Discover or enter the bulb address, query identity/capabilities, obtain the local signing key when required, let the owner identify the intended light, and explicitly adopt it. Persist MAC/model identity separately from its DHCP address. A discovery reply is untrusted network input and must not auto-enroll a device or leak network credentials.

### New or rehomed consumer bulbs

The documented reliable path is WiZ app setup onto the private 2.4 GHz network, followed by local integration adoption and security-key import. WiZ offers Bluetooth-assisted/smart pairing and a manual `WiZConfig_xxxx` access-point flow; the app does not require sign-in for basic installation. This does **not** establish Internet-free commissioning or a public BLE SDK. Official setup may install firmware, during which the bulb can temporarily appear offline. [WiZ installation flow](https://wizconnected.helpshift.com/hc/en/7-wiz-v2/faq/527-adding-wiz-lights-in-your-home/), [pairing troubleshooting](https://wizconnected.helpshift.com/hc/en/7-wiz-v2/faq/489-pairing-troubleshooting-1691160082/)

The current pywizlight source has no implemented consumer Wi-Fi commissioning sequence. A README list containing `setWifiConfig`, discovery of a Bluetooth UUID, or successful association with a bulb's setup AP is not evidence of provisioning. Do not send guessed credentials or reset an installed light while attempting to infer that sequence. The older local gateway experiment also recorded setup-AP association without an accepted `getPilot`/`getSystemConfig` reply and without credentials being sent; that historical experiment is not a paired-light baseline. [Historical experiment record](/Users/achu/Projects/203/firmware/local_gateway/README.md)

For a native app-free pairing promise, the remaining evidence must include the actual device/model's documented or owner-authorized captured provisioning handshake, encryption/authentication, failure/retry behavior, credential storage, firmware differences, and physical completion. A WiZ Pro SDK/cloud workflow must not be substituted for consumer proof.

### Matter

Eligible factory Matter devices with setup codes may use a standard Matter ecosystem. Older compatible devices without the Matter marking need the WiZ V2 app to obtain their device-specific credentials; WiZ documents firmware 1.29.0 or later and a shared local network for setup. Matter's WiZ integration supplies basic power, brightness and color controls, while WiZ-specific dynamic modes and advanced features remain outside that basic contract. Matter is therefore a possible alternative route for compatible models, not proof of full WiZ parity or of obtaining the proprietary UDP home key. [Matter setup](https://wizconnected.helpshift.com/hc/en/7-wiz-v2/faq/594-matter-setup-tips/), [WiZ Matter functions](https://wizconnected.helpshift.com/hc/en/7-wiz-v2/faq/532-what-functions-are-available-when-using-matter-to-control-my-wiz-lights/)

### Independence from WiZ servers

Everyday adopted-bulb control can stay within our Mac/gateway/bulb ecosystem. Our own schedules, favorites, group membership and guest policy can also be local to the gateway. WiZ account administration, native feature configuration and vendor firmware delivery may still need official tools or Internet services. A completely WiZ-cloud-free lifecycle is not established by this research.

If the private bulb LAN is intentionally Internet-isolated, explicitly test timekeeping after total power loss, authenticated command acceptance, native schedules and commissioning/firmware behavior. Do not assume that blocking all vendor traffic preserves every feature. WiZ publishes separate local-control, commissioning, time, firmware and cloud network requirements. [WiZ network configuration guide](https://assets.wizconnected.com/manuals/WiZ-Network-Configuration-v2-01162024.pdf)

## Signed local protocol: exact implementation contract

The pinned upstream adds a `signing_key` constructor argument sourced from the WiZ home local-integration export's `udp_signing_key`. It hex-decodes the key, appends `sigTs` in Unix seconds to a copy of `params`, serializes that object with compact JSON, computes HMAC-SHA256, and Base64-encodes the digest. The outgoing envelope has `method`, `env:"pro"`, `params` and `hmac`. The signature covers **the compact parameters only**, not the entire envelope. [Signing implementation](https://github.com/sbidy/pywizlight/blob/19e607afe0eb6db1473602639e194d691234d4fd/pywizlight/utils.py)

Public upstream known-answer fixture, not a real home secret:

```text
key hex:       00112233445566778899aabbccddeeff
params bytes: {"state":true,"sigTs":1790441723}
HMAC Base64:   vARMv4JpVsxYabcBovABd25ISBzYT8+71v0CUtpU1sg=
```

Use the exact serialized bytes when signing and transmitting. The Python reference preserves insertion order; do not introduce whitespace, sort fields after signing, change number representations, or modify `sigTs` afterward. Native Swift/C implementations should reproduce this fixture and more multi-field/error fixtures. This is an interoperability contract, not a claim of general JSON canonicalization. The displayed vector was independently recomputed with Python's standard-library HMAC during this audit. [Known-answer test](https://github.com/sbidy/pywizlight/blob/19e607afe0eb6db1473602639e194d691234d4fd/pywizlight/tests/test_signing.py)

The README describes an approximately one-minute freshness window, while its fake signed bulb enforces 30 seconds. Neither establishes a universal window for every firmware. Maintain trustworthy current gateway time, distinguish clock failures from key failures, and regenerate timestamps/signatures for safe retries. A monotonic timer must govern network timeouts even when wall-clock time adjusts. Do not blindly replay queued old commands after reconnect. [Signing documentation](https://github.com/sbidy/pywizlight/blob/19e607afe0eb6db1473602639e194d691234d4fd/README.md), [simulated firmware tests](https://github.com/sbidy/pywizlight/blob/19e607afe0eb6db1473602639e194d691234d4fd/pywizlight/tests/test_signing.py)

Important audit boundary: upstream signs outgoing requests, but `_on_response` and the push manager do not authenticate received HMACs. Its signed-bulb test fixture emits signed replies without testing verification of those replies. Our receiver must reject malformed/oversized traffic, bind responses to the expected peer and operation, and implement authenticated response verification where its wire contract is established. Legacy/unverifiable UDP must be treated as unauthenticated local input, not as a trustworthy authorization channel. Never derive guest/admin authority from bulb replies. [Response processing](https://github.com/sbidy/pywizlight/blob/19e607afe0eb6db1473602639e194d691234d4fd/pywizlight/bulb.py), [push receiver](https://github.com/sbidy/pywizlight/blob/19e607afe0eb6db1473602639e194d691234d4fd/pywizlight/push_manager.py)

## Protocol details to preserve in a native implementation

- Use model discovery and graceful method-not-found handling. `getModelConfig` falls back for older firmware; `minDimLevel` is preferable to the upstream fallback of 10 percent. Validate missing, contradictory and out-of-range capability fields.
- The library API's 0–255 brightness abstraction is not the same unit as bulb protocol percentages. Keep conversion centralized; avoid repeatedly quantizing slider state across relay/BLE/UDP.
- Scene catalogs contain static, dynamic, rhythm, custom-mode and sync-product entries. A known ID is not a universal supported-feature declaration.
- Serialize requests per bulb; bound retry count, time and payload size. Coalesce slider updates to the latest desired state and read back the final value. Group success is per member, not transactional.
- A timeout after a write means outcome unknown. Read state before retrying non-idempotent/destructive actions. Do not retry factory reset or firmware operations through a generic control retry loop.
- Registration/push traffic is a convenience for freshness, not device enrollment or security. Reject traffic outside the configured bulb network and maintain a rate limit independent of guest limits.

These are design recommendations informed by the current [bulb implementation](https://github.com/sbidy/pywizlight/blob/19e607afe0eb6db1473602639e194d691234d4fd/pywizlight/bulb.py), [message transport](https://github.com/sbidy/pywizlight/blob/19e607afe0eb6db1473602639e194d691234d4fd/pywizlight/protocol.py), and [vendor message types](https://gitlab.com/wizlighting/wiz-local-control/-/blob/b7bfe09fa480c214d67dcb6b151afef3e0c23416/src/classes/Pilot.ts).

## Admin precedence and external actors

The gateway must enforce permissions, freezes, session revocation, request expiry, replay protection and per-session/device rate limits identically for Internet and Bluetooth. A guest UI cannot be the enforcement boundary. Keep bulb-network credentials and the WiZ home signing key out of guest binaries, responses, logs and diagnostics. Distributing a shared guest password does not justify distributing the admin key or bulb key.

An admin hold overrides commands submitted through our system. It cannot physically prevent power-switch changes, an authorized WiZ app, Matter controller, remote, native schedule or SpaceSense from changing the same bulb. Inventory those writers during setup and clearly report observed external changes. Do not create an aggressive correction loop that fights native automation. A policy to reassert owner state should be explicit, rate limited, visible and bounded.

Our favorites and automation must live on the gateway rather than the menulet, so closing the Mac does not stop them. Reboot recovery needs versioned durable state, a defined safe state when time is unknown, and a consistent rule for missed schedules. Failover between Internet and BLE must preserve request identity and authority; it must not duplicate writes or revive a revoked session.

## Evidence required before claiming production parity

1. Inventory each physical model, firmware, bulb class, zone count, range, signed/unsigned mode, and local security settings. Record read-only results without publishing credentials or full device identifiers.
2. Qualify ordinary power, minimum/maximum brightness, warm/cool limits, RGB, each exposed scene and effect speed with returned state plus physical observation. Verify no effect on the display animation or its firmware recovery path.
3. Exercise old and current firmware fixtures, malformed packets, wrong/missing/stale signing keys, clock jumps, duplicate/out-of-order packets, invalid model metadata and unavailable methods. A fake bulb test is explicitly simulator evidence.
4. Validate private-LAN commissioning on actual owned models. For any official-app step, say so in onboarding; do not mark app-free pairing complete from an AP association or UDP send.
5. Demonstrate radio/campus outage recovery, gateway restart, bulb power loss, DHCP address changes, alternate-transport reconnect and no-Mac operation. Distinguish WiZ vendor-cloud availability from our relay availability.
6. Verify guest freeze, admin precedence, revoked-session rejection, password rotation and command expiry over both transports. Test that no guest receives the WiZ key or raw protocol execution capability.
7. Qualify each persistent/native configuration write separately with read-back, reboot persistence and restoration. Leave unqualified native settings as official-setup-only, even if a library exports the method.

The acceptable initial claim is a native menulet and gateway with validated local core controls and honest, model-aware coverage. Universal official-app parity, universal consumer commissioning, and a wholly vendor-cloud-free lifecycle remain unproven until the corresponding hardware and protocol evidence exists.
